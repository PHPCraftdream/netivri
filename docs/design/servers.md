# Servers: netivri as an entry point

Status: design. Tracks the work of the `servers` series of changes.

## Goal

Today netivri is a client side: apps connect to its local port (SOCKS5, SOCKS4
or HTTP), and their traffic leaves through the route of the account that
logged in. A **server** makes the same routes reachable from other machines
over a VPN-node protocol, so that one netivri on a VPS (or at home) is the
entry point for phones and laptops:

```text
phone (ss://, vless://, ...) -> netivri server -> account route -> [pre] -> node -> [post] -> destination
```

An account without a route leaves directly (or through its `post_socks5`), so
the same feature turns a VPS into a plain exit node.

Acceptance: `netivri server add` + `netivri server link` give a URI that a
stock client of that protocol accepts; the connection is counted and routed as
the owning account; a client address the account does not allow is dropped;
every protocol has a loopback test that drives it with the matching Mihomo
client adapter.

Non-goals (first versions): ACME / Let's Encrypt, an HTTP endpoint that serves
subscriptions, TUN, protocols that need a domain fronting service, a GUI.

## Building blocks already in the tree

- The vendored Mihomo has server listeners for Shadowsocks, VLESS (TLS, WS,
  gRPC, XHTTP, Reality), VMess, Trojan, Hysteria2, TUIC, AnyTLS, Snell, Mieru,
  Sudoku, ShadowQUIC, TrustTunnel and others (`third_party/mihomo/listener`).
  They take a `tunnel` (`C.Tunnel`) and `inbound.Addition` options.
- Accounts are routed by rules `IN-USER,<login>` (`internal/core/accounts.go`),
  and the sticky groups read `metadata.InUser`. A listener that sets `InUser` to
  the account login gets the account's route, statistics, hops and logging for
  free.
- VLESS, VMess and Trojan listeners take a user list and set `InUser` to the
  user's `Username`. Mihomo's Shadowsocks server has a single password, so it
  needs one listener per account, each started with `inbound.WithInUser(login)`.
  Protocols differ here, see the matrix.
- **The IP filter does not cover these listeners.** `inbound.SetAllowedIPs`
  (our `listen.allowed_clients`) is consulted only by the HTTP, SOCKS and mixed
  listeners. A server must enforce `listen.allowed_clients` and the per-account
  `allowed_clients` itself, in the tunnel wrapper it hands to the listener
  (by `metadata.SrcIP` and `metadata.InUser`), before the connection is routed.

## Model

- A **server** is one listening endpoint of one protocol: `name`, `protocol`,
  `bind`, `port`, the accounts it serves, `public_host` (for links) and
  protocol parameters.
- A protocol is **multi-user** (one listener serves many accounts, each with its
  own secret) or **single-user** (one listener per account, so the server names
  exactly one account). The protocol declares which.
- **Secrets are generated by netivri, never typed.** Account passwords are
  argon2id hashes and cannot key a server, so each (server, account) gets its
  own random secret (a key, a UUID or a password, as the protocol needs), and
  each server may have *material* (a Reality key pair and short ids, a TLS
  certificate). Both live in the secrets file, apart from `config.ktav`.

## Config

```text
servers: [
    {
        name: vps-ss
        protocol: shadowsocks
        bind: 0.0.0.0
        port: 8388
        accounts: alice
        public_host: vps.example.org
    }
]
```

- `name`: 1 to 32 characters of `A-Za-z0-9._-`, unique.
- `protocol`: a name from the registry (`netivri server protocols`).
- `bind`: default `0.0.0.0`; `doctor` warns that the port is public.
- `port`: 1 to 65535, required, unique per bind and transport.
- `accounts`: login list, or `*` for every account (multi-user protocols only; a
  single-user protocol needs exactly one login).
- `public_host`: host name or address that links carry; may be empty, then
  `server link --host` is required.
- protocol parameters are keys that the protocol validates (`cipher`, `dest`,
  `sni`, `cert_file`, `key_file`, `obfs`, ...); unknown keys are
  `CONFIG_INVALID` and name the key, never the value.

Validation errors name the key (`servers[1].port`) and never contain a secret.

## Secrets file

`{HOME}/server-secrets.ktav`, mode 0600, written atomically (temp file, fsync,
rename), read only by netivri:

```text
servers: {
    vps-ss: {
        material: { ... }
        users: { alice: { password: ... } }
    }
}
```

- `server add` generates what is missing; `server remove` deletes the entry;
  `server rotate NAME [--account A]` replaces the secret of a user (or the
  material) and reloads the running angel.
- Secrets are never printed except by `server link` (the URI is the point) and
  never written to a log, the state file, `status` or `--json` output of any
  other command.
- A config server without a secrets entry is repaired at `up`; a secrets entry
  without a config server is ignored and reported by `doctor`.

## Package layout

New package `internal/servers`, imported by `internal/core` and `cmd/netivri`:

```go
type Spec struct {
    Name, Protocol, Bind string
    Port                 int
    Accounts             []string          // resolved logins
    Params               map[string]string // validated by the protocol
    Material             map[string]string // generated server-level material
    Users                map[string]map[string]string // login -> secrets
}

type Protocol interface {
    Name() string
    SingleUser() bool
    Validate(params map[string]string) error
    NewMaterial(params map[string]string) (map[string]string, error)
    NewSecret(login string, params map[string]string) (map[string]string, error)
    Start(spec Spec, env Env) (io.Closer, error)
    Link(spec Spec, login, host string) (string, error)
}
```

- `Env` carries the (filtered) `C.Tunnel`, the listen config and the log hooks.
- Protocols register themselves in `init()` (`servers.Register`). A protocol
  change therefore touches only its own files: `internal/servers/<protocol>.go`,
  its tests and `docs/servers/<protocol>.md`. The CLI, `help` and the drift test
  read the registry, so a new protocol appears everywhere without further edits.
- `Link` returns the client URI of the protocol, or, for protocols without a
  standard URI (Snell, Mieru, Sudoku, ShadowQUIC, TrustTunnel), a Mihomo proxy
  snippet; `server link --format uri|mihomo` picks.
- TLS-based protocols share a helper: a self-signed ECDSA P-256 certificate for
  the public host with its SHA-256 fingerprint (pinned in links), or the user's
  `cert_file` / `key_file`. There is no ACME.

## Core wiring

- `core.Options.Servers []servers.Spec`. `Start` starts them after
  `ApplyConfig` and the sticky groups, `Reconfigure` replaces the changed ones
  only (a server whose spec is equal keeps its listener and connections), and
  `Close` stops them before `executor.Shutdown`.
- An address in use is `PORT_IN_USE`, as for the mixed listener; a server that
  fails to start fails `up` (fail closed), a reload that fails keeps the old
  servers and reports the error.
- Every listener gets a wrapped tunnel that (1) drops a client that
  `listen.allowed_clients` or the account's `allowed_clients` does not allow,
  counting the drops, and (2) otherwise passes through to the normal tunnel,
  where rules, sticky groups, hops and `OnConnEvent` apply unchanged.
- UDP: a protocol with a UDP side says so; the loopback tests cover the TCP path
  first, and UDP through a sticky group follows `IsL3Protocol`, which the first
  protocol must verify and document.

## CLI

```text
netivri server protocols [--json]
netivri server add --protocol P [--name N] --account A|* --port N [--bind ADDR]
                   [--public-host H] [--param key=value ...] [--json]
netivri server list [--json]
netivri server show NAME [--json]
netivri server link NAME [--account A] [--host H] [--format uri|mihomo] [--qr]
netivri server rotate NAME [--account A] [--json]
netivri server remove NAME [--json]
```

All take `--home` or `--local`. `add` generates secrets, writes the config and
reloads a running angel; without a name it makes one (`ss-8388`). Exit codes
follow `docs/cli.md`: usage 2, not found for an unknown server, conflict for a
taken name or port, `CONFIG_INVALID` for bad parameters.

`status` lists the servers (name, protocol, listen address, accounts, current
connections, dropped clients). `doctor` checks: secrets file mode, public bind,
port conflicts, certificate expiry, a server whose account no longer exists.

## Logs

One line per event, never a secret, an address or a site: `server vps-ss
(shadowsocks) listening on 0.0.0.0:8388 for account alice`, `server vps-ss
stopped`, `server vps-ss: 14 clients dropped by allowed_clients in the last
minute` (INFO, WARN from 100). Connections of a server go through the same
connection log as the local port, with the account as login.

## Security

- A public port is an authenticated proxy on the internet: secrets are random
  and long, comparison is the listener's own, nothing is logged on a failed
  handshake beyond a count, and protocols that resist active probing (Shadowsocks
  2022, Reality, Trojan fall-through) are preferred in docs.
- `allowed_clients` is enforced before routing, as above.
- `bind` defaults to public because that is the point of a server, and `doctor`
  says so; `--bind 127.0.0.1` keeps it local (the loopback tests use it).
- The secrets file is the only place with secrets; `--local` keeps it inside
  `./.netivri` with the rest.

## Protocol matrix

| Protocol | Users | TLS | Transport | Link |
| --- | --- | --- | --- | --- |
| shadowsocks (2022 and AEAD) | single | no | TCP, UDP | `ss://` |
| vless-reality | multi | Reality (no certificate) | TCP | `vless://` |
| vmess | multi | no (AEAD) | TCP | `vmess://` |
| trojan | multi | TLS material | TCP | `trojan://` |
| hysteria2 | multi | TLS material | QUIC (UDP) | `hysteria2://` |
| tuic | multi (per uuid) | TLS material | QUIC (UDP) | `tuic://` |
| anytls | multi | TLS material | TCP | `anytls://` |
| snell | single | no | TCP | Mihomo snippet |
| mieru | multi | no | TCP, UDP | Mihomo snippet |
| sudoku | single | no | TCP | Mihomo snippet |
| shadowquic | multi | TLS material | QUIC (UDP) | Mihomo snippet |
| trusttunnel | multi | TLS material | TCP | Mihomo snippet |

"multi or single" is the expected model; each protocol task verifies it against
the listener and falls back to one listener per account when the listener does
not name the user. A protocol that cannot be driven on loopback with its Mihomo
client adapter is reported, not shipped untested.

## Tests

- Unit: registry, config and secrets validation, link generation per protocol
  (round trip through the matching URI parser where one exists), the client
  filter.
- Integration, per protocol: the server in one `core.Start`, the matching Mihomo
  outbound adapter as the client, a node recorder as the account's node; checks:
  traffic follows the account's route, a wrong secret is refused, a disallowed
  client is dropped, `Reconfigure` with a rotated secret, `Close` frees the port.
- e2e: a netivri client reaches an echo backend through another netivri's
  server using the link as its subscription (Shadowsocks first, then one TLS and
  one QUIC protocol).
- A drift test: every registered protocol has `docs/servers/<protocol>.md`, an
  index row and a mention in the `server` help topic.

## Delivery

1. Foundation: package, registry, core wiring, client filter, Shadowsocks.
2. In parallel: product (config, secrets store, CLI, status, doctor, logs),
   VLESS Reality, VMess, the TLS material helper.
3. In parallel, after the helper: Trojan, Hysteria2, TUIC, AnyTLS, ShadowQUIC,
   TrustTunnel; and, after the foundation, Snell, Mieru, Sudoku.
4. Docs sweep: index, README, `cli.md`, `config.md`, help, changelog, one full
   CI run, a check on a real machine on a loopback bind.

## Open questions, settled by the first tasks
